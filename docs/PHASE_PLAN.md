## 1. ขอบเขต — และสิ่งที่ *ไม่* อยู่ในขอบเขต

### ✅ อยู่ในขอบเขต

1. ย้ายฐานข้อมูล Sheets → PostgreSQL (Supabase) พร้อม `tenant_id` และ RLS ตั้งแต่ migration แรก
2. เขียน data layer ใหม่ (hydrate/persist) — **ไม่แตะ business logic 300 handlers**
3. Multi-tenant + DevOps Console ขั้นต้น (พอให้รับโรงเรียนที่ 2 ได้)
4. UX/UI ใหม่บน Figma → implement
5. QA ครบทุก Role ทุกฟังก์ชัน
6. ย้ายข้อมูลจริง + คู่ขนาน + ตัดระบบ

### 🚫 ไม่อยู่ในขอบเขต (พูดให้ชัดตั้งแต่ต้น)

| ไม่ทำ | เพราะ |
|---|---|
| **App Store (iOS)** | ต้องมีนิติบุคคล + ค่าธรรมเนียม + รีวิว 1-2 สัปดาห์ · ทำหลังขายได้แล้ว |
| **เขียน frontend ใหม่ทั้งหมด** | 151 routes ใช้สัญญาเดียวกัน — **ย้าย DB ไม่ต้องแตะหน้าจอ** · การออกแบบใหม่เป็นการตัดสินใจเชิงสินค้า ทำแยกและทำเฉพาะหน้าจอที่คุ้ม |
| **AI Agents ครบ 10 ตัว** | เริ่ม 2 ตัวที่คุ้มที่สุด ที่เหลือหลังมีโรงเรียนที่ 3 |
| **เปลี่ยน LINE LIFF** | ประตูของผู้ปกครอง — ห้ามแตะระหว่างย้าย DB ทำทีละอย่าง |
| **เปลี่ยน SlipOK** | เหมือนกัน · ทำงานอยู่ ไม่แตะ |

> ⚠️ **กฎข้อเดียวที่คุมทั้ง 3 เดือน: เปลี่ยนทีละชั้น** · ย้าย DB เสร็จและนิ่งก่อน แล้วค่อยแตะหน้าจอ · ถ้าทำพร้อมกันแล้วช้าลง เราจะไม่รู้ว่าเพราะอะไร

### 🔌 Phase 2 — Data layer + ย้ายข้อมูล (สัปดาห์ 3-6)

หัวใจของทั้งโปรเจ็ค และเป็นส่วนที่ **ไม่แตะ business logic เลย**

| # | งาน | หมายเหตุ |
|---|---|---|
| 2.1 | เขียน `PgEngine` แทน `GasEngine` | รับ `M` แบบเดียวกัน — 300 handlers ไม่รู้ว่าเปลี่ยน |
| 2.2 | Migration script Sheets → Postgres | **แปลง float → numeric ตรงนี้ พร้อมรายงานส่วนต่าง** |
| 2.3 | รัน 143 test suites บน Postgres | **ต้องเขียวทั้งหมด ไม่มีข้อยกเว้น** |
| 2.4 | โหมดคู่ขนาน (dual-write) | เขียนทั้งสองที่ อ่านจาก Sheets |
| 2.5 | Diff checker รายวัน | เทียบทุกตาราง แจ้งเตือนถ้าต่าง |

> 💰 **2.2 คือจุดที่เงินจะเปลี่ยน** — ค่าที่เก็บเป็น float มา 4 ปี เช่น `6899.999999999999` จะกลายเป็น `6900.00` · **ต้องมีรายงานว่าแถวไหนเปลี่ยนไปเท่าไหร่ และ ผอ. ต้องเห็นก่อนตัดระบบ**

### 3 ชั้นที่ต้องผ่านทั้งหมด

| ชั้น | อะไร | ใครทำ | เกณฑ์ผ่าน |
|---|---|---|---|

| **2. เทียบของเก่า** | รัน 151 routes ทั้งบน Sheets และ Postgres แล้วเทียบผลลัพธ์ | ผม | **ผลตรงกันทุก route** |
| **3. คนจริงกดจริง** | ครู/ผู้ปกครอง/ผอ. ใช้งานจริง 1 สัปดาห์ | **พี่จัด** | ไม่มีเรื่องที่ทำไม่ได้ |

### ✅ Checklist ต่อ Role (ชั้นที่ 3)

**ผู้ปกครอง**
- [ ] เข้าผ่าน LINE ได้ · เห็นลูกครบทุกคน
- [ ] เช็คอิน/รับกลับ · **ตรวจว่าค่า OT ตรงกับที่ควรเป็น**
- [ ] แจ้งลา (ทั้งวันเดียวและช่วงวัน) · ยกเลิกได้
- [ ] อ่านสมุดบันทึก · คอมเมนต์ได้
- [ ] ดูบิล · อัปโหลดสลิป · **ยอดเงินตรงทุกบาท**
- [ ] ชำระล่วงหน้า · **ส่วนลดคำนวณถูก**

**คุณครู**
- [ ] ลงเวลาเข้า-ออก · สาย/OT ถูกต้อง
- [ ] เช็คอินแทนนักเรียน · **เวลาที่บันทึกคือเวลาที่กรอก ไม่ใช่เวลาที่ส่งถึงเซิร์ฟเวอร์**
- [ ] สมุดบันทึกประจำวัน (ร่าง → ส่ง → ล็อก)
- [ ] ประเมิน DSPM · แจ้งอุบัติเหตุ · ยื่นใบลา
- [ ] ติดตามการขาดเรียน · OT นักเรียน

**หัวหน้าครู** — ทุกข้อของครู + อนุมัติขั้นที่ 1 + ดูข้ามห้อง
**ผอ./Leader** — อนุมัติขั้นที่ 2 + รายงานทั้งโรงเรียน + เงินเดือน
**Observer** — เห็นทุกอย่าง **แก้ไม่ได้แม้แต่อย่างเดียว** (ทดสอบด้วยการพยายามแก้)
**Admin** — ทุกเมนู + ออกบิล + payroll + จัดการผู้ใช้

### 🔴 5 อย่างที่ต้องทดสอบด้วยของจริง ไม่ใช่ของจำลอง

1. สลิปจริง → SlipOK → Drive
2. OT รับช้าครั้งแรกของจริง
3. รอบบิลจริงเดือนแรก
4. **เงินเดือนจริง 1 รอบ — เทียบกับที่จ่ายจริงทุกบาท**
5. แจ้งอุบัติเหตุจริง (LINE push ถึงจริง)

> ⚠️ ข้อ 4 สำคัญที่สุด · **ถ้าเงินเดือนคลาดแม้ 1 สตางค์ ห้ามตัดระบบ**

## 4. UX/UI บน Figma

### ลำดับงาน

```
1. Audit หน้าจอปัจจุบัน  →  2. Design system  →  3. Wireframe  →
4. UI จริง  →  5. Prototype กดได้  →  6. ทดสอบกับคนจริง  →  7. ส่งมอบ
```

### สิ่งที่พี่ต้องทำ

| ขั้น | พี่ต้องทำอะไร | ใช้เวลา |
|---|---|---|
| **1** | สร้างบัญชี Figma (ฟรีพอ) + เชิญผม | 10 นาที |
| **2** | **ตัดสินใจเรื่องแบรนด์**: สีหลัก, โลโก้, ฟอนต์ไทย | 1-2 ชม. |
| **3** | รีวิว wireframe → บอกว่าอะไรผิดจากการใช้งานจริง | 2 ชม./รอบ |
| **6** | **หาครู 2 คน + ผู้ปกครอง 3 คน มากด prototype ต่อหน้า** | ครึ่งวัน |

> 🎯 **ขั้นที่ 6 คือขั้นที่มีค่าที่สุด และเป็นขั้นที่คนมักข้าม** · ให้เขากดเองโดยเราไม่บอกอะไร แล้วดูว่าเขาติดตรงไหน — **ห้ามอธิบาย ห้ามช่วย** จดว่าเขาหยุดตรงไหน

### กฎการออกแบบที่ยึดไว้แล้ว (`FRONTEND_DESIGN.md`)

> **"อ่านออกจากระยะแขน กลางแดด มือเดียว ขณะอุ้มเด็กอยู่"**

- Mobile first เสมอ (Android 65% ของ traffic)
- ปุ่มที่ทำเรื่องเงิน ต้องมีคำอธิบายใต้ปุ่มว่าทำอะไร
- ปุ่มสำคัญอยู่ล่าง (นิ้วโป้งอยู่ตรงนั้น)
- ข้อความ error ต้องบอกว่า**ทำอะไรต่อ** ไม่ใช่แค่บอกว่าผิด

## 5. สิ่งที่พี่ต้องทำ — เรียงตามลำดับเวลา

### 🔴 สัปดาห์นี้ (ก่อนผมเริ่มได้)

1. **หมุน Google backup codes** — ไฟล์รหัสกู้คืนยังอยู่ใน git history ของ repo สาธารณะ · **ทุกอย่างของ Supabase แขวนอยู่บนบัญชีนี้**
2. **สร้าง Supabase org + project** (ฟรี ไม่ต้องใส่บัตร) แล้วเชิญผม
3. **เลือกชื่อแบรนด์** จาก 10 ชื่อใน `BRAND_NAMING.md` แล้วตรวจ 3 ข้อ (เครื่องหมายการค้า · โดเมน · handle)

### 🟡 ภายในเดือนแรก

4. **ร่างข้อตกลง PDPA** กับทนาย — *ห้ามนำข้อมูลนักเรียนจริงขึ้น Supabase ก่อนข้อนี้เสร็จ*
5. **ให้แต่ละ Role อ่านคู่มือของตัวเอง** (`docs/spec/roles/`) แล้วยืนยันว่าถูก — **ถ้าคู่มือผิด ระบบใหม่จะผิดตาม**
6. สร้างบัญชี Figma + ตัดสินใจเรื่องแบรนด์

### 🟢 เดือนที่ 2-3

7. รีวิว design ทุกรอบ
8. **จัดคนมาทดสอบ prototype** (ครู 2 + ผู้ปกครอง 3)
9. **ตรวจรายงานส่วนต่างตัวเลขเงิน** หลัง migration — *ข้อนี้พี่ต้องดูเอง ผมตรวจแทนไม่ได้*
10. จัดสัปดาห์ทดสอบของจริง
11. **อนุมัติตัดระบบ** — เป็นการตัดสินใจของพี่ ไม่ใช่ของผม
